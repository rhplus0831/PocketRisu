# MessagePack remediation work-priority index

Generated 2026-08-01 from the 30 verified findings (15 client, 15 server) and the re-validated prior-report claims consolidated in [messagepack-memory-performance-audit.md](messagepack-memory-performance-audit.md); remediation status was last updated 2026-08-02. The audit's Part 4 solution tracks resolve to **32 work items**: **3** correctness hazards in Tier 0, **27** assigned to active resource tiers, **1** deferred architectural migration, and **1** cross-cutting validation suite; **17 remain unresolved, including 1 deferred, and 15 are resolved**. Two high-severity findings (C4, C8) have no Part 4 track item; this index defines their remediation. `Cn`/`Sn` identifiers refer to the audit's Part 2/Part 3 finding tables and "claim N" to its Part 1 verdict table; the prior report [plugin-storage-inline-memory-performance.md](plugin-storage-inline-memory-performance.md) remains the detailed inline-pipeline reference. Status uses `Ready` for items implementable directly from the audit's remediation, `Needs design` for items requiring a design pass or a coordinated protocol/format change first, `Deferred` for valid work intentionally held outside the active execution order until it is explicitly reprioritized, and `Resolved` for implemented items with regression coverage. All items were classified on 2026-08-01 against `8a385fad`; findings are point-in-time evidence and must be re-verified against current code before work begins.

## Priority rules

| Tier | Meaning |
|---|---|
| Tier 0 | The finding's failure mode is wrong or lost data rather than resource exhaustion; the fix is small and precedes all performance work. |
| Tier 1 | The issue drives **client (browser) memory** usage and can culminate in a tab out-of-memory crash that makes the application unusable. |
| Tier 2 | The issue drives **client CPU** usage: main-thread stalls, boot latency, jank during streaming or editing. |
| Tier 3 | The issue drives recurring **client/server network traffic**. |
| Tier 4 | The issue drives **server CPU** usage: event-loop blocking, avoidable cryptographic or codec work, N+1 scans. |
| Tier 5 | The issue drives **server memory** usage: payload-sized request buffering and retention leaks. |

The ordering follows the plan's core principle: first prevent client-side out-of-memory failures that can make the application unusable; next improve responsiveness by reducing CPU usage and network traffic; finally optimize server-side memory consumption. Three adjustments were applied to that baseline. First, a Tier 0 was added for the audit findings whose dominant harm is data integrity, not resources (C12 stale-block resurrection, C14 persistence abort, S11 stale-cache persistence) — scheduling them behind performance work would leave silent correctness hazards open, and all three are small bounded fixes. Second, multi-axis items are classified by their dominant harm with secondary axes noted in the Impact column; several Tier 1 and Tier 4 items also carry network or memory benefits. Third, server ingress buffering (S2) stays in Tier 5 per the baseline, but leads that tier and may justifiably be pulled forward in execution because unbounded pre-auth buffering is also a denial-of-service exposure for externally reachable instances — the audit's own sequencing ranks it third for that reason.

## Completed remediations

These items are implemented and covered by regressions, so they no longer participate in the active execution order. Three formerly made up Tier 0; Tracks 1.1, 1.3, 1.5, 1.7, 2.2, 2.5, 3.1, and 3.4, the client half of Track 5.4, and the bounded C4 cache staging work were the first resource remediations.

Regression coverage proves the first cached read after a full write is a decoded-cache hit with the acknowledged ETag while correctly rebuilding segment bytes for the new publication. |
| [Admit before buffering](messagepack-memory-performance-audit.md#track-3--bounded-ingress-and-streaming-reads) (Track 3.1) | S2 | Resolved | Bodies up to 2 GiB buffered before route-level auth and before storage-queue admission, so queued writers could accumulate payload-sized Buffers and expose externally reachable instances to ingress denial of service. | Fixed: one pre-parser admission layer authenticates matching JWT/cookie routes, rejects `sessionLock.peek()`-stale writers without changing writer authority, requires exact uncompressed `Content-Length`, applies route-specific database/chat/KV/proxy/plugin/JSON ceilings, and reserves declared bytes from a 512 MiB process-wide budget until response finish or connection close. ## Suggested execution order

Tier position ranks user impact; execution order additionally weighs cost, risk, and shared code, and may pull a cheap lower-tier item forward when it rides an in-flight change.

1. **Pure work-removal quick wins are complete**: the streaming JSON validator now covers single-row mutations (Track 3.4), joining the full-write double decode, parse-once decoding, deferred full-save assembly, and all three Tier 0 correctness hazards.
2. **Remaining Tier 1 design work** starts with binary plugin-value transport and bounded conflict recovery. All Tier 1 `Ready` items are resolved: resource-cache boot staging, narrow snapshots, and the msgpackr target cap.
3. **Remaining Tier 2 client CPU**, beginning with dirty revisions once their correctness fallback is in place, followed by the coordinated codec-worker design. (Active-chat reactive re-walks are resolved.)
4. **Remaining Tier 4 server read/patch lifecycle** (chat-row serving and protected-read streaming), then the background subsystems (snapshots, chat backups, viewer, metadata sizes; the manifest cache is resolved). Generation-aware `dbCache` reuse and encoded-segment memoization are resolved. The ETag rework and any other client-visible protocol changes ride coordinated releases.
5. **Remaining Tier 5 large-ingress spooling and legacy bounding**. Admission-before-buffering and its denial-of-service hardening are resolved; admitted database/chat bodies still need the coordinated disk-spool design before their per-request memory and event-loop work are bounded.
6. **Tier 3 chat delta persistence** lands last among the active items as a coordinated format/protocol migration, preceded by its Track 6 budget test.

Deferred architectural migrations are not part of this execution order. If residency decoupling is reprioritized, its Track 6 budget scenarios must precede implementation.
