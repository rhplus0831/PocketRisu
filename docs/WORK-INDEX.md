# MessagePack remediation work-priority index

Generated 2026-08-01 from the 30 verified findings (15 client, 15 server) and the re-validated prior-report claims consolidated in [messagepack-memory-performance-audit.md](messagepack-memory-performance-audit.md). The audit's Part 4 solution tracks resolve to **32 work items**: **3** correctness hazards in Tier 0, **27** assigned to active resource tiers, **1** deferred architectural migration, and **1** cross-cutting validation suite; **27 remain unresolved, including 1 deferred, and 5 are resolved**. Two high-severity findings (C4, C8) have no Part 4 track item; this index defines their remediation. `Cn`/`Sn` identifiers refer to the audit's Part 2/Part 3 finding tables and "claim N" to its Part 1 verdict table; the prior report [plugin-storage-inline-memory-performance.md](plugin-storage-inline-memory-performance.md) remains the detailed inline-pipeline reference. Status uses `Ready` for items implementable directly from the audit's remediation, `Needs design` for items requiring a design pass or a coordinated protocol/format change first, `Deferred` for valid work intentionally held outside the active execution order until it is explicitly reprioritized, and `Resolved` for implemented items with regression coverage. All items were classified on 2026-08-01 against `8a385fad`; findings are point-in-time evidence and must be re-verified against current code before work begins.

## Priority rules

| Tier | Meaning |
|---|---|
| Tier 0 | The finding's failure mode is wrong or lost data rather than resource exhaustion; the fix is small and precedes all performance work. |
| Tier 1 | The issue drives **client (browser) memory** usage and can culminate in a tab out-of-memory crash that makes the application unusable. |
| Tier 2 | The issue drives **client CPU** usage: main-thread stalls, boot latency, jank during streaming or editing. |
| Tier 3 | The issue drives recurring **client/server network traffic**. |
| Tier 4 | The issue drives **server CPU** usage: event-loop blocking, avoidable cryptographic or codec work, N+1 scans. |
| Tier 5 | The issue drives **server memory** usage: payload-sized request buffering and retention leaks. |

The ordering follows the plan's core principle: first prevent client-side out-of-memory failures that can make the application unusable; next improve responsiveness by reducing CPU usage and network traffic; finally optimize server-side memory consumption. Three adjustments were applied to that baseline. First, a Tier 0 was added for the audit findings whose dominant harm is data integrity, not resources (C12 stale-block resurrection, C14 persistence abort, S11 stale-cache persistence) — scheduling them behind performance work would leave silent correctness hazards open, and all three are small bounded fixes. Second, multi-axis items are classified by their dominant harm with secondary axes noted in the Impact column; several Tier 1 and Tier 4 items also carry network or memory benefits. Third, server ingress buffering (S2) stays in Tier 5 per the baseline, but leads that tier and may justifiably be pulled forward in execution because unbounded pre-auth buffering is also a denial-of-service exposure for externally reachable instances — the audit's own sequencing ranks it third for that reason.

These items are implemented and covered by regressions, so they no longer participate in the active execution order. Three formerly made up Tier 0; Tracks 1.1 and 1.3 were the first Tier 1 remediations.

| Work item | Findings | Status | Impact | Resolution |
|---|---|---|---|---|
| [Defer full-save assembly to the fallback](messagepack-memory-performance-audit.md#track-1--remove-avoidable-client-work-no-format-or-protocol-changes) (Track 1.1) | Prior report Phase 1; claim 7 | Resolved | Every save assembled a complete fallback buffer before the patch attempt — a payload-sized transient allocation per save on large databases. | Fixed: `encoder.set()` still maintains blocks before patch generation, while `encoder.encode()` now runs only after patching has selected an ETag-guarded or forced full write. The real client save-loop performance harness proves a successful unrelated patch performs no full assembly, while a known patch rejection and a forced write each assemble and publish exactly once. |
| [Parse strict-decode blocks once](messagepack-memory-performance-audit.md#track-1--remove-avoidable-client-work-no-format-or-protocol-changes) (Track 1.3) | C1 | Resolved | Cache-off boot of a block-format row overlapped input bytes, every block string, a discarded validation graph, and the final graph on the main thread, with parse work done twice. | Fixed: authoritative client decoding parses and consumes each known JSON block once during the framing scan, skips content decoding for unknown future blocks, and fetches remote bodies only when they are ready to be consumed. Whole-block and whole-database logs are development-gated. Regression coverage counts exactly one parse per known block while the authoritative integrity suite continues to cover malformed, incomplete, future, and cache-isolation cases. |
| [Scope and bound `risuSaveCacheMap`](messagepack-memory-performance-audit.md#track-1--remove-avoidable-client-work-no-format-or-protocol-changes) (Track 1.4) | C12 | Resolved | Stale cached blocks can be resurrected even during strict authoritative decoding, and deleted characters' JSON is retained for the tab lifetime. | Fixed: the cache is reset with each encoder generation, entries are evicted with blocks and on `cache: false`, root JSON is not retained, and strict decoding never consults recovery state. Regression coverage primes the cache before testing authoritative rejection. |
| [Fix mechanical encode hazards](messagepack-memory-performance-audit.md#track-1--remove-avoidable-client-work-no-format-or-protocol-changes) (Track 1.6) | C14, C15, claim 5 | Resolved | A broad lorebook shift can abort persistence through the spread-argument limit; map16 overflow throws only after encoding completes; decoded binary subarrays and header slices can pin their entire source buffer. | Fixed: per-character patches use loop appends and fall back atomically to one normalized, stub-only character replacement above 32,768 operations or 8 MiB; client/server transport codecs support standard map32 values; long-lived legacy and cached-segment decodes copy binary values without adding a second cache-miss copy. Regression coverage exercises patch convergence, the 65,536-key codec boundary, detached binary ownership, and the 100,000-entry real-server boundary. |
| [Canonicalize storage-key identity on the server](messagepack-memory-performance-audit.md#track-2--server-readpatch-lifecycle) (Track 2.4) | S11 | Resolved | An alias `dbCache` entry keyed by noncanonical hex survives canonical invalidation and its persist timer can write stale data. | Fixed: accepted hex paths are decoded once and re-encoded to one lower-case identity before cache, memo, or timer access while case variants remain wire-compatible. Real-server regressions prove mixed-case patches share one baseline and a noncanonical patch timer cannot overwrite a later full write. |

## Suggested execution order

Tier position ranks user impact; execution order additionally weighs cost, risk, and shared code, and may pull a cheap lower-tier item forward when it rides an in-flight change.

1. **Remaining pure work-removal quick wins**: the full-write double decode and the streaming JSON validator. This matches the unresolved portion of the audit's quick-win set and removes server-write waste without format changes — while, as the audit notes, leaving steady browser retention in place. (Parse-once decoding, deferred full-save assembly, and all three Tier 0 correctness hazards are resolved.)
2. **Remaining Tier 1 `Ready` items** (resource-cache boot staging, narrow snapshots, msgpackr target cap), with design started in parallel on binary plugin-value transport and bounded conflict recovery.
3. **Tier 2 client CPU**, beginning with chat revision signals; dirty revisions follow only once their correctness fallback is in place.
4. **Tier 4 server read/patch lifecycle** (`dbCache` reuse, segment memoization, chat-row serving, protected-read streaming), then the background subsystems (snapshots, chat backups, manifest, viewer, metadata sizes). The ETag rework and any other client-visible protocol changes ride coordinated releases.
5. **Tier 5 ingress hardening and legacy bounding**, with the caveat above: for externally reachable or Hub-hosted deployments, admission-before-buffering is also denial-of-service hardening and can be scheduled alongside step 2.
6. **Tier 3 chat delta persistence** lands last among the active items as a coordinated format/protocol migration, preceded by its Track 6 budget test.

Deferred architectural migrations are not part of this execution order. If residency decoupling is reprioritized, its Track 6 budget scenarios must precede implementation.
