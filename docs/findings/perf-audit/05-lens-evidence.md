## placement

```text
ANSWER:
Findings:
1. BOOT-DEFAULTS — Cold boot compares the post-default/migration graph with the pre-default server baseline, so missing defaults and per-character migrations become startup dirty work despite no user edit. Evidence: `src/ts/bootstrap.ts:157-183` captures the baseline before `setDatabase`; `src/ts/storage/database.svelte.ts:42-126,409-475,768-799` fills missing roots and plugin fields; `src/ts/bootstrap.ts:560-584,659-731` fills per-character fields and runs a second `setDatabase`; `src/ts/globalApi.svelte.ts:424-526` compares the live graph and marks branches dirty. Waste: W2. Severity: S3; scales with missing/defaulted graph fields and characters. Fix direction: establish the authoritative baseline after idempotent boot normalization, or send only a narrowly scoped migration patch. Invariant risk: BLOCKED-NEEDS-DESIGN because this changes stub/placeholder and publication-baseline semantics.
2. BOOT-PATCH-SCALE — The DB-scaled cold upload can be the JSON `/api/patch` request itself: if character IDs/order change, `RisuSavePatcher` emits one whole `/characters` replacement; otherwise per-character migration fields accumulate across all characters. Evidence: `src/ts/storage/risuSave.ts:1857-1901` emits the whole-character-array replacement on structural change and `:1903-1972` emits per-character diffs; `src/ts/globalApi.svelte.ts:868-873,1036-1045` sends that proposal; `src/ts/storage/nodeStorage.ts:5307-5321` serializes/uploads the patch JSON to `/api/patch`. This explains the 300-character versus 10-character scaling when a fresh context still has legacy/missing IDs or fields; after the first successful save, the next reload has the normalized baseline, so only a small patch remains. Waste: W2. Severity: S3; scales with character count and changed per-character bytes. Fix direction: normalize/assign durable IDs before capturing the comparison baseline and suppress no-op migration diffs. Invariant risk: BLOCKED-NEEDS-DESIGN because patching touches stub guards, publication atomicity, and commit-outcome handling.
3. BOOT-FULL-FALLBACK — A full DB-sized upload is exactly `/api/write` with the encoded stub-only database when patch sync is forced or a patch is rejected. Evidence: `src/ts/globalApi.svelte.ts:1068-1088` selects the full path and calls `forageStorage.setItem` with `dbData`; `src/ts/storage/nodeStorage.ts:3064-3089` sends the bytes to `/api/write`; the normal patch path is `:1036-1045`. Direct source evidence does not identify the rejection/force condition responsible for the measured cold run, so this is a conditional explanation rather than a proven attribution. Waste: W2. Severity: S3; scales with encoded `database.bin` bytes. Fix direction: instrument the rejection code and keep valid startup migrations on patch-only paths. Invariant risk: BLOCKED-NEEDS-DESIGN because full-write fallback is the stub/publication atomicity boundary.

Waste: W2. Severity: S3; scales with database size. Fix direction: avoid rewriting the monolith unless the plugin publication actually changed, while preserving the paired publication transaction. Invariant risk: BLOCKED-NEEDS-DESIGN because publication atomicity and commit-outcome protocols are directly involved.

Evidence: `src/ts/storage/chatPersistStage.ts:75-116` detects full chats differing from the persisted baseline; `:255-301` writes each candidate; `src/ts/globalApi.svelte.ts:841-853` invokes the stage; `src/ts/storage/nodeStorage.ts:6142-6150,6243-6253` POSTs one full `/api/chat-content/<cha>/<index>` row when no smaller delta is usable. Invariant risk: BLOCKED-NEEDS-DESIGN because stub/placeholder guards, publication atomicity, and commit-outcome rules apply.

UNRESOLVED:
No repository request log or performance fixture identifies the exact A1/A5 upload route sequence and body sizes.
The source proves conditional /api/write full uploads but does not prove which patch rejection, forced reconciliation, or migration condition occurred in the measured A5 run.
The source cannot determine whether the measured 300-character instances lacked durable chaId values, had per-character legacy fields missing, or contained full non-placeholder chat bodies; each has a distinct scaling path.
The exact number of unrelated boot requests contributing to the reported 34-request A1 total is not derivable from loadData() alone because plugin loading and other startup helpers are outside the supplied boot trace.
```

## adoption

```text
ANSWER:
Findings:

1. A3-chat-delta-adoption — The first post-hydration save is not inherently baseline-less: successful chat hydration verifies the server hash and records an acknowledged snapshot (`nodeStorage.ts:6110-6118`), while an in-session full write records one only after an exact hash acknowledgement (`nodeStorage.ts:6255-6263`). Therefore the first-save baseline failure is conditional: missing/invalid `x-content-hash`, hash mismatch, or a different storage instance; code does not support “only a prior full write can establish it.” Delta admission still requires `previous && requestHash && prepared.patch` (`nodeStorage.ts:6208-6208`), a message-only patch (`chatDelta.ts:39-46`), byte-identical replay (`payloadCodecOperations.ts:54-66`), and a smaller JSON body (`nodeStorage.ts:6217-6219`). Ordinary streaming sends always toggle `isStreaming` and its optimization mode (`index.svelte.ts:1548-1550`, `:1684-1685`); those are non-message diffs and make `prepareChatDeltaPatch()` return null. Input/output hooks can also mutate `scriptstate` (`triggers.ts:1202-1206`), while `name`, `lastDate`, `folderId`, and `modules` are likewise outside the permitted patch paths. Current code has no ordinary-send client assignment to `chat.lastDate`; the only server assignment found is cold-storage restoration (`server.cjs:18140-18144`). Thus the “virtually every real streaming send” inference is supported by `isStreaming`, but the measured failing-provider case remains unresolved without the request trace proving baseline state and the exact diff.
Waste W2; severity S2, scaling with encoded active-chat row bytes. Fix direction: define a persisted-row projection that excludes runtime-only fields or broaden the delta protocol with exact replay coverage, while retaining hash/size/replay guards. Invariant risk: BLOCKED-NEEDS-DESIGN (serialization and never-replay contract).

2. A3-two-full-writes — User input appends a message (`chatSendTarget.ts:164-168`), the active-chat tracker queues a chat save (`globalApi.svelte.ts:665-693`), and the 500 ms debounce marks the save loop dirty (`globalApi.svelte.ts:580-597`). During a live generation, the first candidate is written because no checkpoint timestamp exists (`chatPersistStage.ts:260-296`). The stage deliberately requeues throttled-generation chats (`chatPersistStage.ts:260-265`), and generation completion re-arms the tracker and schedules another save (`globalApi.svelte.ts:600-609`); the non-throttled final pass writes again (`chatPersistStage.ts:283-297`). This explains the observed checkpoint-plus-final pair when timing allows both saves. Each save prepares a full encoded row and falls back to it whenever delta admission fails (`nodeStorage.ts:6204-6249`). Waste W2; severity S2, scaling with active-chat encoded bytes and one exchange’s save count. Fix direction: make checkpoint/final persistence use a delta-safe persisted projection or coalesce the first/final write only where durability semantics permit. Invariant risk: BLOCKED-NEEDS-DESIGN (checkpoint durability and final-response durability).

3. server-chunk-plan-adoption — The worker planner exists (`chunkPlan.cjs:78-93`), and its prepared branch avoids CDC/SHA inside publication (`chunkStore.cjs:1444-1458`), while the null-plan branch performs synchronous FastCDC and SHA in the transaction (`chunkStore.cjs:1459-1475`). Multiple sibling paths publish with no plan: automatic snapshot publication (`server.cjs:1500-1501`, `:1613-1622`), optimized boot cleanup (`server.cjs:6194-6204`), streamed plugin batch/single mutations (`server.cjs:13180-13191`, `:13667-13677`), both transition finalizers (`server.cjs:14945-14953`, `:15140-15149`), and backup-import rows (`server.cjs:4480-4482`, `:4571-4572`). These execute under storage mutation/publication turns, so large values hold the FIFO while synchronous planning runs. Waste W6; severity S2 for plugin mutations/transitions and S3-S4 for snapshots/imports, scaling with affected bytes and row count. Fix direction: prepare worker plans before queue entry, then pin/revalidate source identity at publication. Invariant risk: BLOCKED-NEEDS-DESIGN (publication atomicity and source revalidation).

4. generic-plugin-validation — Generic spooled `/api/write` validates plugin rows by reading the entire spool into memory (`server.cjs:16011-16019`), whereas the streamed plugin batch hashes and validates staged rows incrementally (`server.cjs:12909-12933`) and the shared validator is explicitly streaming (`importSpool.cjs:291-301`). Waste W4; severity S2, scaling with plugin-row bytes. Fix direction: use the streaming validator for generic plugin-row ingress before publication. Invariant risk: low, provided validation remains before queue publication.

5. legacy-manifest-echo — The legacy full-manifest route commits rows and the manifest but returns only `{ success: true }` (`server.cjs:13952-13974`). Its client helper therefore invalidates the cached manifest revision before dispatch (`pluginSaveStorage.ts:1562-1578`). Callers include database-bridge replacement/compatibility writes (`pluginSaveStorage.ts:2138-2153`, `:2182-2192`), hashed and non-generation set/remove (`pluginSaveStorage.ts:2434-2472`, `:2610-2638`), owner set/remove (`pluginSaveStorage.ts:3790-3808`, `:3831-3841`), clear/clear-owned (`pluginSaveStorage.ts:3418-3429`, `:3444-3459`), and boot recovery’s non-mapped pair writes (`pluginSaveStorage.ts:5651-5668`, `:5782-5783`). The next ownership operation must re-read authoritative state. Waste W1/W5; severity S2, scaling with plugin key count and mutation frequency. Fix direction: add a validated manifest-revision echo to the legacy acknowledgement or migrate all callers to the revision-bound mutation protocol. Invariant risk: BLOCKED-NEEDS-DESIGN (publication atomicity and outcome protocol).

6. duplicate-ownership-reads — `clearPluginSaveStorage()` reads ownership before calling the legacy mutation helper (`pluginSaveStorage.ts:3418-3428`), and `setPluginSaveStorageOwner()` does the same (`pluginSaveStorage.ts:3790-3808`); `commitOptimizedStorageMutation()` then performs another `readCurrentOwnership()` for the same operation (`pluginSaveStorage.ts:1536-1553`). This is two ownership reads per clear/owner-set invocation. Waste W1/W4; severity S2, scaling with externalized plugin key count. Fix direction: pass a freshness-stamped ownership snapshot into the mutation helper and retry only on a proven revision conflict. Invariant risk: BLOCKED-NEEDS-DESIGN (freshness/publication protocol).

7. plugin-codec-worker-adoption — Bulk transition preparation synchronously MessagePacks each row (`pluginStorageTransitionBulk.ts:173-184`) and hashes it (`:220-227`) on the caller path (`nodeStorage.ts:2250-2265`). Batch preparation hashes each value and metadata (`nodeStorage.ts:3401-3417`); compatibility fallback synchronously encodes and hashes the complete request (`:3418-3424`). The existing `PayloadCodecService` exposes worker-backed operations only for chat encoding/checkpoints and strict block decoding (`payloadCodecService.ts:184-224`); these plugin paths do not use it. Waste W4; severity S2, scaling with plugin row count and total encoded bytes. Fix direction: add immutable plugin encode/hash operations to the codec worker, preserving Blob ownership and exact request hashes. Invariant risk: design required for rich-value compatibility and byte ownership, but no direct stub-guard change is evidenced.

Unresolved: static code proves the streaming-send delta rejection and the checkpoint/final save mechanism, but cannot identify why the provider-failure trace used a full row if hydration had already recorded a valid acknowledgement; capture the baseline-map state, `x-content-hash`, and prepared patch reason for that request. Static code also does not prove an ordinary send updates `lastDate`; only cold-storage restore does.

UNRESOLVED:
The provider-failure full-row trace cannot be attributed statically to baseline absence versus another delta precondition; capture acknowledgedChatRows state, x-content-hash, and prepared.patch reason for that request.
No ordinary-send client assignment to chat.lastDate was found; current code only directly assigns it during server cold-storage restoration.
```

## concurrency

```text
ANSWER:
Findings:
1. LB-COND-001 Asset GC: queueStorageMutation spans flush, DB decode, asset/plugin-reference scan, candidate bookkeeping, and deletes (server/node/server.cjs:7213-7282). Hold scales with DB/plugin bytes, asset count, candidates, and deletions; scan permits up to 2,000,000 nodes. W6, S4. Hazard H4/H3: avoid stale references and deletion races. Fix: scan outside the FIFO using DB/plugin reference tokens and asset identities, then revalidate before candidate updates/deletes. Risk high because no single durable token currently covers all external plugin-value references.
2. LB-COND-002 Chat pre-images: every eligible overwrite streams the old row, fsyncs, and atomically renames while the mutation FIFO is held (server/node/server.cjs:18269-18311, 18360-18390, 18435-18496; server/node/chatBackups.cjs:825-889). Hold scales with old chat-row bytes, plus small-row decode cost. W6/W4, S2. Hazard H1/H2/H4: exact recovery pre-image and ordering immediately before overwrite. Fix: pin bytes with rowToken/snapshot outside the FIFO; revalidate the token at publish, retry or fail closed on mismatch; required deletion captures must remain durable before row deletion. Risk high.
3. LB-COND-003 Chat-backup reconciliation: the queued operation performs directory discovery, frame conversion, legacy-bundle migration, per-chat trimming, global-budget eviction, and repeated tree scans (server/node/chatBackups.cjs:1407-1459, 1275-1390). Hold scales with backup file count and total backup bytes; global eviction can rescan the tree after each removal. W6, S2. Hazard H1/H2/H4: durable, non-conflicting recovery history. Fix: serialize capture and reconciliation with a dedicated backup-filesystem mutex; do scanning/conversion/trim outside the storage FIFO and retain only short atomic publication/rename sections. Risk medium-high.
4. LB-COND-004 Deferred patch persistence: persistDbCacheGeneration can encode the full DB while queued and also captures deletion pre-images before its commit (server/node/server.cjs:2426-2503); the patch response path can itself retain/compute the full canonical encoding inside the queue (server/node/server.cjs:16834-16860, 16887-16894). W6/W4/W3, S2, scaling with DB bytes and deleted chat-row bytes. Hazard H4/H9/H10 plus H1/H2 and plugin-publication atomicity. Fix: prepare encoding/externalization/deletion plans outside the FIFO; use existing cache generation, DB revision, cache identity, and publication tokens for an O(1) commit gate, then publish in one transaction. Risk high because dirty cache, plugin rows, chat rows, and database.bin must remain one publication.
5. LB-COND-005 Chat-log compaction: compactChatRow materializes the base plus operation log inside the queued callback, although publishCompactedChatRow already has an exact rowToken check (server/node/server.cjs:18252-18262; server/node/chatRows.cjs:874-910). W6/W4, S2, scaling with base-row and operation-log bytes. Hazard H4/H1: stale compaction must not overwrite newer deltas, and base/log replacement must be transactional. Fix: materialize outside the FIFO and reuse the existing token-conditional publish transaction. Risk medium.
6. LB-COND-006 Inlay reference maintenance: authoritative inlay scans decode every physical chat row and parse messages while queued; deletion repeats that scan before deleting up to 1,000 IDs (server/node/server.cjs:3643-3665, 3686-3705, 11143-11180). W6/W4, S2-S3, scaling with chat-row count, chat-row bytes, and message count. Hazard H4/H3: prevent deletion racing a newly referenced inlay or import. Fix: scan a pinned snapshot outside the FIFO, retain chat-row/source tokens, and revalidate them before deletion; abort/retry on mismatch. Risk medium-high because DB revision alone covers database.bin, not external chat rows.
7. LB-COND-007 Protected plugin manifest/recovery paths: manifest mutation decodes the full live database inside the FIFO after already decoding the request plan outside it (server/node/server.cjs:13858-13894); boot reconciliation similarly reads and decodes database.bin and inspects external rows while queued (server/node/server.cjs:6222-6244, 6316-6332). W6/W4, S3-S4, scaling with DB/plugin-row bytes. Hazard H4/H9/H10/H2: generation/manifest state must match the atomic publication. Fix: pin raw DB and publication revisions, validate outside the FIFO, then compare revision/manifest tokens before the atomic write; retry on divergence. Risk high.
kvCleanupOldDeletions is not a confirmed finding: db.cjs opens one writable better-sqlite3 connection, cleanup is one synchronous DELETE, and the seven-day tombstone retention exceeds the six-day delta eligibility window (server/node/db.cjs:34, 80-84, 909-910; server/node/listDelta.cjs:3-17, 38-96). It can technically execute during an import and join that transaction because the hourly caller bypasses the FIFO (server/node/server.cjs:21228-21231; server/node/importBarrier.cjs:7-19), but no compound invariant or acknowledged user-data mutation is evident; keeping it outside avoids adding W6. No PT finding: the session lock is the O(1) single-writer boundary, not a phantom guard.

UNRESOLVED:
No runtime benchmark or production fixture was available, so exact milliseconds are not evidenced; the hold shapes are asymptotic/code-derived.
Asset GC needs a durable or composite reference token for database.bin plus external plugin values before discovery can safely leave the FIFO.
No targeted test was found for hourly deletion cleanup firing during a long import; current evidence shows the effect is operational tombstone cleanup, not live user-data mutation.
```

## cache

```text
ANSWER:
F-A2-1: Claim: A warm segmented boot can cost more bytes than raw boot for small databases. Evidence: `src/ts/storage/nodeStorage.ts:4412-4501` always performs one POST cached-read when enabled, builds a JSON hash inventory, then falls back to a second raw GET on failure; `server/node/dbCachedRead.cjs:50-67` caps advertisements at 8192 hashes and `:319-323` emits `{hash}` or `{bytes}` segments. Derived overhead using this MessagePack shape: advertisement ≈103 + 67H bytes (H hashes; cap ≈548,967 bytes); warm envelope ≈97 + 72N bytes (N total segments including root; `{hash}` is 72 bytes). Network-only crossover is raw bytes R > about 200 + 139N; at N=8192 this is ≈1.14 MB. The measured 8.6 KB advertisement corresponds to roughly 127 advertised hashes if it is only the DB inventory; 11.5 KB received corresponds to roughly 158 all-hit segments, or fewer hits plus miss bytes.
```
